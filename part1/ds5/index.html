1왜 필요한가

04장의 배열은 크기가 고정이었다. 이 장에서는 스스로 커지는 배열을 만든다.

1.1 크기를 미리 모를 때

03장에서 “제약 조건의 최댓값으로 전역 배열을 잡는다”를 배웠다. 대부분의 문제에서 이것으로 충분하다. 그런데 통하지 않는 경우가 있다.

상황왜 고정 배열로 곤란한가
배열이 여러 개 필요한데
각각의 크기를 모른다		“각 그룹에 속한 원소들”처럼 그룹이 N개면 배열도 N개다. 모두 최댓값으로 잡으면 N × N칸이 되어 메모리가 터진다
총합만 제한되어 있다“모든 그룹의 원소 수 합이 20만 이하”라면 전체로는 작은데, 그룹별 최댓값을 모르니 고정 크기를 정할 수가 없다
입력을 끝까지 읽어야
개수를 안다		개수를 알려 주지 않고 EOF까지 읽으라는 문제
자료구조 안에서 쓴다스택은 Vec의 끝 연산으로 쉽게 만들 수 있다. 큐·덱은 앞쪽 접근도 필요하므로 원형 버퍼(머리·꼬리 인덱스)를 추가하거나 다른 구현을 사용한다

1.2 PART 1의 출발점

이 장이 특별한 이유는 다음 세 장에서 필요한 동적 저장과 확장의 기초를 다루기 때문이다. 스택은 Vec의 끝 연산을 활용하고, 큐·덱은 원형 버퍼 구조를 더 배우게 된다.

그래서 이 장의 Vec은 뒤의 자료구조를 설계할 때 재사용할 수 있는 기본 코드다. 다만 큐·덱·그래프에서는 요구 연산에 맞게 구조를 조정해야 한다. 베껴 쓰지 말고 손에 익혀야 한다.

2개념과 그림

2.1 Vec은 세 가지를 들고 다닌다

동적 배열의 정체는 단순하다. 배열 하나와 숫자 두 개를 묶은 것이다.

이름뜻왜 필요한가
a실제 값이 담긴 배열데이터 본체. malloc으로 얻은 메모리를 가리킨다
n길이 — 지금 들어 있는 개수어디까지가 진짜 값인지 알아야 한다
cap용량 — 담을 수 있는 최대 개수언제 늘려야 하는지 알아야 한다

2.2 가득 차면 무슨 일이 일어나는가

C에서 잡아 둔 메모리를 그 자리에서 늘릴 수 있다는 보장은 없다. 바로 뒤에 다른 데이터가 있을 수 있기 때문이다. 기존 공간을 확장할 수 없다면 다음 세 단계를 거친다.

① 더 큰 방을 빌린다

새 크기만큼 메모리를 새로 잡는다

② 짐을 옮긴다

기존 값 n개를 새 배열로 복사한다 — 여기가 비용

③ 옛 방을 반납한다

이전 메모리를 free한다

②의 복사가 O(n)이므로 늘리는 순간의 push는 O(n)이다. 그런데도 평균이 O(1)이 되는 것이 이 장의 핵심이고, 비밀은 “얼마나 늘리느냐”에 있다.

realloc이 세 단계를 한 번에 해 준다

C에는 realloc(ptr, 새크기)가 있어 ①②③을 알아서 처리한다. 운이 좋아 뒤에 빈 공간이 있으면 옮기지 않고 그 자리에서 늘리기도 하므로 직접 하는 것보다 빠를 때가 많다. 다만 반환값을 받는 방식에 함정이 있다 — 3.2절에서 다룬다.

2.3 얼마나 늘릴 것인가 — 가장 중요한 선택

가득 찼을 때 용량을 얼마로 키울 것인가. 가장 자연스러워 보이는 “한 칸만 더”와 “두 배로”를 비교해 보자. 아래는 초기 용량 1에서 매번 새 배열을 잡아 복사하는 방식의 예시 측정값이다. 컴퓨터·컴파일러에 따라 시간은 달라진다. 본문 3절의 Vec은 처음 용량을 4로 잡으므로 횟수가 다르다.

$ ./grow2    (gcc -std=c11 -O2)

+1 증가    N =    50,000 :   108.1 ms    새 배열 5만 회    총 복사 약 12.5억 칸
+1 증가    N =   100,000 :   434.7 ms    새 배열 10만 회   총 복사 약 50억 칸
방식새 배열 만든 횟수총 복사 칸 수push 1회 평균전체
+1씩N번1+2+…+(N−1) ≈ N²/2O(N)O(N²)
2배씩약 log₂N번1+2+4+…+N ≈ 2NO(1)O(N)

숫자로 확인되는 것

+1 방식은 N이 2배(5만 → 10만)가 될 때 시간이 108 ms → 435 ms로 4배가 되었다. 전형적인 O(N²)의 신호다. 반면 2배 방식은 10배 더 큰 N = 100만을 3 ms에 끝냈다. 같은 일을 하는데 입력이 10배 작은 쪽이 145배 느리다.

2.4 왜 2배면 평균 O(1)인가 — 분할 상환

용량을 2배로 늘리며 N번 push했다고 하자. 재할당 때 실제로 새 공간으로 옮긴다고 가정하면, 복사될 수 있는 기존 원소 수는 1, 2, 4, 8, …처럼 증가한다.

1 + 2 + 4 + … + 2k−1 = 2k − 1 < 2N

마지막으로 복사가 발생한 기존 용량은 N보다 작으므로, 전체 복사 칸 수는 2N 미만이다. 새 원소를 쓰는 N번까지 더해도 총비용은 O(N), 즉 push 한 번당 분할 상환 O(1)이다. 이는 임의 입력에 대한 단순 산술 평균이나 모든 push가 O(1)이라는 뜻이 아니다. 예를 들어 초기 용량 1에서 N = 1,000,000이면 재할당 횟수 21회, 최대 복사량은 1,048,575칸이다. 아래 구현처럼 초기 용량 4면 증가 횟수 19회, 최대 복사량은 1,048,572칸이다. realloc이 제자리 확장에 성공하면 실제 복사량은 더 적을 수 있다.

분할 상환(amortized)이라는 말

“어쩌다 한 번 비싼 연산이 있지만, 여러 번에 나눠 보면 평균은 싸다”는 뜻이다. 용량을 늘리는 그 한 번의 push는 분명 O(n)이다. 하지만 그런 일은 2배씩 드물게 일어나므로 전체로 보면 상수가 된다.

비유하자면 1년에 한 번 큰돈을 내는 보험료를 12로 나눠 매달 조금씩 내는 것과 같다. 비싼 달이 분명 있지만 평균 월납은 작다. 이 개념은 재할당·재해싱과 크기 조절을 분석할 때 다시 쓰인다.

Q. 3배나 10배로 늘리면 더 좋지 않나요?
성장 시 재할당 횟수는 줄지만 쓰지 않는 메모리가 늘어날 수 있다. 10배로 늘리면 원소 101개를 담으려고 1,000칸을 잡게 된다. 2배는 복사 비용과 메모리 낭비 사이의 균형점이라 널리 쓰인다. 1.5배를 쓰는 라이브러리도 있는데, 메모리를 덜 쓰는 대신 복사가 조금 늘어난다.

3.1 구조체와 생성 · 해제

/* vec.c — 정수를 담는 동적 배열 (1/3) */
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>     /* SIZE_MAX */
#include <limits.h>     /* INT_MAX */

typedef struct { int *a; int n, cap; } Vec;

static void vec_error(const char *msg) {
    fputs(msg, stderr);
    fputc('\n', stderr);
    exit(EXIT_FAILURE);
}

static void vec_init(Vec *v, int cap) {
    if (cap < 0 || (size_t)cap > SIZE_MAX / sizeof(int))
        vec_error("잘못된 초기 용량");
    v->a = NULL; v->n = 0; v->cap = 0;
    if (cap == 0) return;
    v->a = malloc((size_t)cap * sizeof *v->a);
    if (v->a == NULL) vec_error("초기 할당 실패");
    v->cap = cap;
}

static void vec_free(Vec *v) {
    free(v->a);
    v->a = NULL;
    v->n = v->cap = 0;
}

sizeof(int)를 꼭 곱한다

malloc이 받는 것은 바이트 수다. sizeof(int)==4인 환경에서 int 100개는 400바이트다. (size_t) 형변환은 올바른 크기 계산에 도움이 되지만, 곱셈의 오버플로 자체를 막지는 않는다. 할당 전에 cap <= SIZE_MAX / sizeof(int)를 확인해야 한다.

해제 뒤 NULL을 넣는 이유

free한 포인터를 다시 free하는 것은 정의되지 않은 동작이다. 반드시 오류 메시지와 함께 종료되는 것은 아니다. free(NULL)은 안전하므로 같은 Vec의 재해제 실수를 줄이기 위해 NULL을 넣는다. 단, Vec 구조체를 단순 대입으로 복사한 별칭 포인터까지 안전해지는 것은 아니다.

3.2 늘리기와 push

/* vec.c — 용량 확장과 push (2/3) */
static void vec_grow(Vec *v) {
    /* int 곱셈이 발생하기 전에 검사 */
    if (v->cap > INT_MAX / 2)
        vec_error("int 용량 범위 초과");
    int nc = (v->cap == 0) ? 4 : v->cap * 2;
    /* size_t 바이트 수 계산 전에 검사 */
    if ((size_t)nc > SIZE_MAX / sizeof *v->a)
        vec_error("할당 크기 범위 초과");
    int *nb = realloc(v->a, (size_t)nc * sizeof *v->a);
    if (nb == NULL) vec_error("재할당 실패");
    v->a = nb;
    v->cap = nc;
}

static void vec_push(Vec *v, int x) {
    if (v->n == v->cap) vec_grow(v);
    v->a[v->n++] = x;
}

반드시 임시 포인터로 받는다 — 가장 흔한 버그

/* 틀림 */
v->a = realloc(v->a, 새크기);
/* 맞음 */
int *nb = realloc(v->a, 새크기);
if (nb == NULL) { ... }
v->a = nb;

크기가 0보다 큰 재할당이 실패하면 NULL이 오고 기존 메모리는 그대로 유효하다. 왼쪽처럼 쓰면 그 주소를 영영 잃어버린다.

처음 용량을 0이 아니라 4로 잡는 이유

0에서 2배를 하면 계속 0이다. 첫 증가만 특별히 처리한다. 이 구현은 첫 할당을 4칸으로 하고, 이후 8·16·32칸으로 늘린다. 초기 용량을 크게 정하면 작은 입력에서 재할당 횟수를 줄일 수 있지만 미사용 공간은 늘어날 수 있다.

3.3 꺼내기와 읽기

/* vec.c — 읽기와 꺼내기 (3/3) */
static int vec_pop(Vec *v) {
    if (v->n == 0) vec_error("빈 Vec에서 pop");
    return v->a[--v->n];
}

static int vec_at(const Vec *v, int i) {
    if (i < 0 || i >= v->n)
        vec_error("Vec 인덱스 범위 초과");
    return v->a[i];
}

static int vec_empty(const Vec *v) {
    return v->n == 0;
}

pop은 용량을 줄이지 않는다

n만 하나 줄일 뿐 메모리는 그대로 둔다. 줄였다가 다시 push가 오면 또 늘려야 하고, 늘렸다 줄였다를 반복하면 복사가 끝없이 일어난다. 01장에서 쓴 ADT 명세표의 “결과” 칸으로 말하면 “크기 1 감소, 용량은 변하지 않음”이다.

3.4 동작 확인

1부터 10까지 제곱수를 넣으며 길이와 용량이 어떻게 변하는지 찍어 본다.

읽어야 할 세 가지

  • 용량이 늘어나는 순간은 4, 8, 16 — 10번 push하는 동안 세 번뿐이다
  • 늘어난 뒤에는 n만 증가하고 cap은 가만히 있다 — 대부분의 push는 공짜다
  • pop 뒤에도 cap은 16 그대로다

실험할 때 주의 — 한 printf에 pop을 넣지 않는다

위 출력을 만들 때 printf("pop=%d n=%d", vec_pop(&v), v.n)처럼 쓰면 단순히 이전 값이 찍히는 것이 아니라, 함수 인자 평가 사이에서 같은 v.n을 순서 없이 읽고 수정하므로 정의되지 않은 동작이다. int last = vec_pop(&v);를 먼저 실행하고 printf("pop=%d n=%d", last, v.n);처럼 출력한다.

3.5 C11에서 바로 실행하는 main()

3.1~3.3절의 함수들을 같은 C 파일에 순서대로 넣고, 맨 아래에 다음 main을 붙이면 3.4절의 실행 결과를 직접 확인할 수 있다. main 없이 함수 정의만 저장한 파일은 실행 파일로 링크할 수 없다.

/* vec.c — 앞의 함수 정의 아래에 붙이는 main */
int main(void) {
    Vec v;
    vec_init(&v, 0);
    printf("초기      : n=%d cap=%d\n", v.n, v.cap);
    for (int i = 1; i <= 10; ++i) {
        int x = i * i;
        vec_push(&v, x);
        printf("push %2d -> n=%2d cap=%2d\n", x, v.n, v.cap);
    }
    printf("at(3) = %d\n", vec_at(&v, 3));
    int last = vec_pop(&v);
    printf("pop() = %d  -> n=%d cap=%d\n", last, v.n, v.cap);
    printf("empty() = %d\n", vec_empty(&v));
    vec_free(&v);
    printf("해제 후   : n=%d cap=%d\n", v.n, v.cap);
    return 0;
}

몇 번째 pushcap 변화이때 복사한 칸이유

예제 2 realloc 함정

다음 코드의 문제점을 찾고 고쳐라. 메모리가 부족해 realloc이 실패했을 때 무슨 일이 일어나는지 설명할 것.

void grow(Vec *v){
    v->cap *= 2;
    v->a = realloc(v->a, (size_t)v->cap * sizeof(int));
}

풀이. 핵심 오류는 두 가지이며, 여기에 용량 계산의 오버플로 검사 누락도 있다.

  • ① 실패를 확인하지 않는다. realloc이 NULL을 돌려주면 그 NULL이 v->a에 덮인다. 그런데 실패했을 때 원래 메모리는 멀쩡히 살아 있다. 주소를 잃었으므로 되찾을 수도 free할 수도 없고, 다음 push에서 NULL에 값을 쓰다 죽는다
  • ② cap을 먼저 바꿨다. 실패하면 실제 용량은 그대로인데 cap만 2배로 기록되어, 있지도 않은 칸에 값을 쓰게 된다
void grow(Vec *v) {
    if (v->cap > INT_MAX / 2) vec_error("용량 초과");
    int nc = v->cap ? v->cap * 2 : 4;
    if ((size_t)nc > SIZE_MAX / sizeof *v->a)
        vec_error("바이트 수 초과");
    int *nb = realloc(v->a, (size_t)nc * sizeof *v->a);
    if (nb == NULL) vec_error("재할당 실패");
    v->a = nb;
    v->cap = nc;   /* 성공한 뒤에 갱신 */
}

예제 3 배열 여러 개 — 1.1절의 상황

그룹이 N개(N ≤ 200,000) 있고, 각 그룹에 원소를 넣으라는 지시가 M번(M ≤ 200,000) 들어온다. 어느 그룹에 몇 개가 들어갈지는 미리 알 수 없다. (1) int g[200000][200000]은 왜 안 되는가? (2) 어떻게 해결하는가?

풀이. (1) 칸 수가 400억 개, int로 약 149 GB다. 메모리 제한 256MB의 600배 수준이라 선언 자체가 불가능하다.

static Vec g[200000];                    /* 구조체 배열은 전역에 */

for (int i = 0; i < N; i++) vec_init(&g[i], 0);  /* 처음엔 전부 빈 Vec */

    int grp = fast_in(), x = fast_in();
    vec_push(&g[grp], x);                 /* 0 <= grp < N 확인 필요 */
}

메모리 계산. 일반적인 64비트 환경에서는 Vec 구조체가 16바이트(포인터 8 + int 4 + int 4)이므로 20만 개면 약 3.2MB다(환경에 따라 달라짐). 값 자체는 M개 이하이지만, 이 구현은 첫 삽입 시 각 Vec이 최소 4칸을 할당한다. 만약 20만 그룹에 하나씩 넣으면 총 80만 칸 = 3.2MB가 할당되고, 개별 malloc 호출의 관리 비용도 추가된다. 따라서 5MB 남짓이라고 단정할 수 없다. 그래도 149GiB짜리 정적 2차원 배열보다 훨씬 작다. 그룹이 매우 많으면 하나의 큰 배열을 공유하는 노드 풀 방식도 고려한다.
