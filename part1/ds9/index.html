1왜 필요한가

05~08장에서 만든 것은 전부 배열 위에 있었다. 배열은 빠르지만 중간을 건드리는 일에 약하다. 이 장은 그 약점 하나를 해결하고, 대신 무엇을 잃는지 정확히 재는 장이다.

1.1 배열이 못 하는 것 하나

배열 가운데에 값을 하나 끼워 넣으려면 뒤쪽을 전부 한 칸씩 밀어야 한다. 한 번은 괜찮다. 문제는 그것을 N번 할 때다.

$ ./mid      가운데에 N번 끼워 넣기
        n      배열(ms)        배열 이동량   리스트(ms)   리스트 링크 갱신
    50000          39.1          625,000,000          0.3        100,000
   100000         183.7        2,500,000,000          0.2        200,000
   200000         785.5       10,000,000,000          0.3        400,000

위 시간은 특정 컴퓨터에서 얻은 예시 측정값이며 기기·컴파일러·측정 코드에 따라 달라진다. 비교 조건은 삽입할 위치의 앞 노드를 이미 알고 있고 탐색 시간은 제외한 경우다. N = 200,000일 때 배열은 약 100억 칸을 이동하지만 리스트는 링크를 40만 번 갱신한다. 삽입 위치를 찾아야 한다면 리스트도 O(N)이 추가된다.

1.2 연결 리스트의 발상

배열의 약속

“i번째 다음은 i+1번째다.” 순서가 위치로 정해져 있다. 그래서 중간에 끼우려면 위치를 전부 바꿔야 한다.

리스트의 약속

“각 값이 다음이 누구인지 들고 있다.” 순서가 링크로 정해져 있다. 끼우려면 링크 두 개만 고치면 된다.

이 맞바꿈에는 분명한 대가가 있다. 배열은 a[k]로 어디든 한 번에 갈 수 있지만, 리스트는 첫 노드부터 k번 따라가야 k번째에 닿는다. 그래서 이 장의 복잡도 표는 이긴 칸과 진 칸이 반씩이다(4.1절).

1.3 그리고 이 장의 진짜 주제 — 노드 풀

교과서는 연결 리스트를 malloc과 포인터로 가르친다. 대회에서는 노드 풀을 자주 사용한다. 배열 두 개로 구현할 수 있다.

$ ./bench      n = 1,000,000
malloc  리스트 : 생성    30.0 ms     노드당 메모리 32.1 바이트
노드 풀 리스트 : 생성     4.6 ms     노드당 메모리 8 바이트
                       예시 측정에서 6.5배 빠름          배열 원소 크기는 약 1/4

위 수치는 한 환경의 벤치마크 예시이지 모든 환경에서 보장되는 속도·메모리 비율이 아니다. 구현 방식과 할당기에 따라 달라진다. 지금은 한 줄만 기억하면 된다 — 노드 풀은 “노드를 미리 배열로 만들어 두고 번호로 부르는 것”이다. 이 기법은 10장 이중 연결 리스트, 21장 체이닝 해시, 32장 트라이까지 그대로 쓰인다.

2.1 노드와 링크

2.2 논리적 순서 ≠ 물리적 순서

이 장에서 가장 중요한 그림이다. 아래는 10 → 15 → 20 → 30 순서인 리스트를 노드 풀로 만든 실제 배열 상태다.

$ ./pool
head -> 10 -> 15 -> 20 -> 30 -> NIL        ← 논리적 순서

  i   :    0    1    2    3    4
  val :    0   30   20   10   15           ← 배열에 담긴 순서
  nxt :    3   -1    1    4    2

배열에는 30, 20, 10, 15 순으로 들어 있는데 리스트는 10, 15, 20, 30으로 읽힌다. 논리적 순서는 nxt[]를 따라 결정되며, 물리적 노드 번호 순서와 일치할 필요가 없다.

단계지금 번호값다음으로 갈 번호
시작0 (더미)—nxt[0] = 3
1310nxt[3] = 4
2415nxt[4] = 2
3220nxt[2] = 1
4130nxt[1] = −1 → 끝

여기서 나오는 질문 두 개

  • 왜 순서가 뒤죽박죽인가? 30, 20, 10을 맨 앞에 차례로 넣었기 때문이다. 노드 생성 순서는 30(1번), 20(2번), 10(3번)이고, 15는 나중에 4번 노드로 생성해 10과 20 사이에 끼워 넣었다.
  • 그래서 문제가 되나? 정답에는 영향이 없다. 다만 속도에는 영향이 있다 — 4.3절에서 같은 노드로 5.9배 차이를 측정한다.

2.3 더미 헤드 — 특수 처리를 없애는 장치

더미 헤드는 값이 없는 가짜 노드 하나를 리스트 맨 앞에 영구히 두는 것이다. 노드 한 개를 더 쓰는 대신 얻는 편의가 크다.

상황더미가 없으면더미가 있으면
맨 앞에 삽입head 자체를 바꿔야 한다 → 함수에 head의 주소를 넘기거나 반환값으로 돌려받아야 한다insert_after(head, v) — 다른 위치와 완전히 같다
맨 앞 삭제head = head->next 특수 분기erase_after(head) — 같은 함수
빈 리스트head == NULL 검사를 곳곳에nxt[head] == NIL로 검사

핵심 한 줄

모든 삽입·삭제를 “어떤 노드의 뒤에”로 통일하면, 더미 덕분에 맨 앞도 “더미의 뒤”가 되어 특수한 경우가 사라진다. 단일 연결 리스트는 뒤로만 갈 수 있으므로, 애초에 지울 노드가 아니라 그 앞 노드를 잡는 것이 올바른 설계다.

2.4 노드 풀 — 왜 malloc을 안 쓰는가

노드 풀은 노드를 미리 배열로 다 만들어 두고, 포인터 대신 번호를 쓰는 것이다. NULL의 자리는 −1이 대신한다.

/* 교과서 방식 */
typedef struct Node {
    int v;
    struct Node *next;
} Node;

Node *p = malloc(sizeof *p);
if (p == NULL) { perror("malloc"); exit(EXIT_FAILURE); }
p->next = NULL;    /* stdlib.h 필요 */
/* 대회 방식 — 노드 풀 */
static int val[MAXNODE];
static int nxt[MAXNODE];
static int cnt;

int p = cnt++;
nxt[p] = NIL;   /* NIL 은 -1 */
항목malloc 노드노드 풀근거 (4.4절 실측)
생성 속도30.0 ms4.6 ms100만 개 기준 6.5배
노드당 메모리32.1 바이트8 바이트sizeof는 16인데 실제는 32 — 관리 비용이 붙는다
해제free 필요개별 free 없음고정 풀은 프로그램 종료 시 반환하며, 삭제 노드 재사용에는 별도 빈 칸 목록이 필요
디버깅주소를 봐야 한다printf로 번호배열을 통째로 찍어 볼 수 있다 (2.2절 표)

정직하게 — 노드 풀이 이기지 못하는 칸도 있다

제시된 실험에서는 순회 시간이 비슷했다(43.0 ms 대 41.1 ms). 그러나 할당 방식·노드 배치·캐시 상태에 따라 순회 속도는 달라진다. 또 노드 풀은 최대 개수를 미리 알아야 하고, 지운 노드의 칸을 그냥 두면 낭비된다(연습 05). 노드 풀의 진짜 강점은 속도보다 메모리와 단순함이다.

3.1 노드 풀과 리스트 만들기

/* list.c — 배열 두 개로 만드는 단일 연결 리스트 */
#include <stdio.h>
#include <stdlib.h>
#define MAXNODE 1000005
#define NIL (-1)

static int val[MAXNODE];      /* 값 */
static int nxt[MAXNODE];      /* 다음 노드의 '번호' (없으면 NIL) */
static int cnt;               /* 다음에 쓸 빈 칸 */
static int head;              /* 더미 헤드의 번호 */

static int new_node(int v){
    if (cnt >= MAXNODE) {
        fprintf(stderr, "노드 풀 용량 초과\n");
        exit(EXIT_FAILURE);
    }
    val[cnt] = v;  nxt[cnt] = NIL;  return cnt++;
}
static void list_init(void){
    cnt = 0;  head = new_node(0);     /* 0번 칸을 더미로 쓴다 */
}

왜 0번을 더미로 쓰는가

cnt가 0부터 시작하므로 맨 처음 만든 노드가 자연스럽게 0번이 된다. 그러면 head는 언제나 0이고, 어디서든 0을 더미로 믿을 수 있다.

3.2 삽입 · 삭제 · 탐색

static void insert_after(int p, int v){   /* p 의 '뒤'에 v 를 끼운다 */
    int q = new_node(v);
    nxt[q] = nxt[p];        /* ① 새 노드가 p 의 다음을 이어받고 */
    nxt[p] = q;             /* ② 그 다음에 p 가 새 노드를 가리킨다 */
}
static void erase_after(int p){           /* p 의 '다음'을 지운다 */
    int q = nxt[p];
    if (q == NIL) return;               /* 지울 것이 없다 */
    nxt[p] = nxt[q];        /* q 를 논리적 리스트에서 제외; 풀의 칸은 재사용 안 함 */
}
static int  find_prev(int v){            /* 값이 v 인 노드의 '앞'을 찾는다 */
    for (int p = head; nxt[p] != NIL; p = nxt[p])
        if (val[nxt[p]] == v) return p;
    return NIL;                           /* 없음 */
}
static void traverse(void){
    for (int p = nxt[head]; p != NIL; p = nxt[p]) printf("%d ", val[p]);
}

순서를 바꾸면 리스트가 끊어진다

insert_after에서 ①과 ②를 바꿔 nxt[p]=q;를 먼저 하면, nxt[p]의 원래 값이 사라져 뒤쪽 전체를 잃는다. “끊기 전에 먼저 붙잡아라” — 3.3절 역순 연결에서 똑같은 규칙이 다시 나온다.

Q. find_prev는 왜 val[nxt[p]]를 보나요? val[p]가 자연스러운데요.
지운다·끼운다를 하려면 그 노드가 아니라 그 앞 노드가 필요하기 때문이다. 단일 연결 리스트는 뒤로만 갈 수 있어 “앞으로 돌아가기”가 불가능하므로, 찾을 때부터 한 칸 앞을 들고 있는다. 10장에서 이 불편이 사라진다.

3.3 역순 연결 — 포인터 세 개

리스트를 통째로 뒤집는다. 새 노드를 하나도 만들지 않고 링크 방향만 바꾼다. 필수 구현 항목이고, 면접·대회에서 가장 많이 나오는 리스트 문제다.

static void reverse(void){
    int prev = NIL, cur = nxt[head];
    while (cur != NIL) {
        int after = nxt[cur];    /* ① 먼저 '다음'을 붙잡아 둔다 */
        nxt[cur] = prev;         /* ② 방향을 뒤집는다 */
        prev = cur;              /* ③ 두 포인터를 한 칸씩 전진 */
        cur  = after;
    }
    nxt[head] = prev;            /* ④ 마지막에 있던 것이 새 첫 노드 */
}
$ ./rev
원래              head -> 10 -> 20 -> 30 -> 40 -> 50 -> NIL
reverse 뒤        head -> 50 -> 40 -> 30 -> 20 -> 10 -> NIL
한 번 더          head -> 10 -> 20 -> 30 -> 40 -> 50 -> NIL

n = 1,000,000 역순 검증 : 정확 (확인한 노드 1,000,000개)

①을 빼면 어떻게 되는지 — 실제로 돌려 본 결과

after를 쓰지 않고 nxt[cur]=prev;를 먼저 한 뒤 cur=nxt[cur];를 하면, nxt[cur]는 이미 prev로 바뀌어 있다.

원래              head -> 10 -> 20 -> 30 -> 40 -> 50 -> NIL
reverse_bug 뒤    head -> 10 -> NIL        ← 뒤가 통째로 사라졌다

무한 루프도, 오류 메시지도 없다. 조용히 노드 네 개가 없어진다. 이것이 포인터 버그의 전형적인 모습이다 — 터지지 않고 결과만 틀린다.

4.1 이긴 칸과 진 칸

연산배열연결 리스트설명
k번째 값 읽기O(1)O(N)리스트의 가장 큰 약점 — 처음부터 따라가야 한다
맨 앞 삽입·삭제O(N)O(1)배열은 전부 민다
맨 뒤 삽입O(1)O(N) 또는 O(1)tail을 따로 들고 있으면 O(1)
중간 삽입·삭제
(앞 노드를 알고 있을 때)		O(N)O(1)리스트의 주요 장점
값으로 찾기O(N)O(N)둘 다 전부 본다
순회 1회O(N) · 빠름O(N) · 느림같은 O(N)인데 상수가 다르다 (4.3절)

“위치를 이미 알 때”가 핵심 조건이다

중간 삽입이 O(1)인 것은 삽입·삭제 위치의 바로 앞 노드 번호를 이미 알고 있을 때뿐이다. 값으로 찾아서 끼운다면 찾는 데 O(N)이 들어 전체는 O(N)이 된다. 이 조건을 빠뜨린 채 “리스트가 빠르다”고 외우면, 실제로는 배열보다 느린 코드를 짜게 된다.

4.2 중간 삽입 — 1.1절 표를 다시 본다

        n      배열(ms)        배열 이동량   리스트(ms)   리스트 링크 갱신
    50000          39.1          625,000,000          0.3        100,000
   100000         183.7        2,500,000,000          0.2        200,000
   200000         785.5       10,000,000,000          0.3        400,000

두 열을 비교해 읽는다

  • 배열 이동량은 n²에 비례한다. n이 2배가 될 때 6.25억 → 25억 → 100억으로 정확히 4배씩 늘었다 — O(N²)의 교과서적 모습이다
  • 리스트 링크 갱신 횟수는 2N이다. 삽입 한 번에 링크 두 개. n=200,000이면 400,000으로 정확히 맞는다
  • 리스트 시간은 n이 4배가 되어도 측정값은 0.2~0.3 ms 수준이었다. 실제 연산 수는 N에 비례하므로 입력이 커지면 시간이 증가한다

4.3 순회가 느린 진짜 이유

같은 O(N)이더라도 리스트 순회는 배열보다 느릴 수 있다. 왜인지 정확히 알기 위해 노드 값과 노드 수를 같게 만들고 재 보았다 — 같은 노드 풀, 같은 100만 개 노드, 같은 합계. 주된 차이는 링크를 따라가는 순서이다.

$ ./shuffle      n = 1,000,000, 순회 20회
노드 풀 · 링크 순서 = 배열 순서 :    38.9 ms

04장에서 2차원 배열을 열 우선으로 순회했을 때와 같은 현상이다. CPU는 메모리를 한 칸씩이 아니라 덩어리로 읽어 온다. 링크가 순서대로면 이미 읽어 둔 덩어리 안에서 다음 노드를 찾지만, 링크가 멀리 뛰면 매번 새로 읽어 와야 한다.

Q. 그러면 노드 풀을 쓰면 항상 빠른 건가요?
아니다. 위 두 줄은 똑같은 노드 풀이다. 풀을 쓰는 것만으로는 부족하고, 접근 순서와 메모리 배치가 비슷할수록 캐시 효율이 좋아질 가능성이 크다. 입력 순서대로 리스트를 만들면 대개 저절로 그렇게 되지만, 중간 삽입을 많이 하면 점점 흐트러진다. 그럼에도 리스트를 선택할 수 있는 이유는 삽입 위치를 알고 있을 때 링크 갱신만으로 중간 삽입이 가능하기 때문이다 — 무엇을 많이 하는 문제인가로 고른다.

4.4 메모리 — 노드 풀을 쓰는 가장 큰 이유

$ ./mem
sizeof(Node)            = 16 바이트   (int 4 + 패딩 4 + 포인터 8)
노드 풀 1개분 (4바이트 int 2개) = 8 바이트

malloc 노드 1,000,000개 실제 사용량 : 31,372 KB -> 노드당 약 32.1 바이트
노드 풀  1,000,000개 배열 원소 크기  :  약 7,812 KiB -> 원소당 8 바이트

256MB 제한에서 담을 수 있는 노드 수
  malloc 노드 : 약   836만 개 (측정 예시)
  노드 풀     : 약 3,355만 개 (배열만 계산)

sizeof와 실제 메모리 사용량은 다를 수 있다

malloc은 블록마다 “이 블록이 몇 바이트인지” 같은 관리 정보를 함께 저장하고, 정렬을 위해 크기를 올려 잡는다. 그래서 작은 블록을 많이 잡으면 추가 비용이 커질 수 있다. 제시된 환경에서는 실제 메모리 증가량이 노드당 약 32.1바이트였지만 항상 32.1바이트인 것은 아니다.
결론. sizeof(Node)는 구조체 자체의 크기이고, malloc 관리 비용·정렬·할당기 특성은 별도다. 또한 /proc/self/statm은 Linux의 프로세스 메모리 통계로, 개별 할당 블록의 정확한 크기를 직접 알려 주지는 않는다.

7도전 문제

C1정렬된 두 리스트 병합
오름차순으로 정렬된 두 리스트 A, B가 있다. 값을 담는 새 노드를 만들지 않고, 기존 노드의 링크만 변경하여 두 리스트를 합쳐 하나의 정렬된 리스트를 만들라. |A| + |B| ≤ 1,000,000.
예 : A = 1 4 7 9, B = 2 3 8 10 11 → 1 2 3 4 7 8 9 10 11
(1) 기존 A 리스트의 더미 헤드를 결과 리스트의 더미로 재사용하면 코드가 얼마나 짧아지는가? 더미 없이 짜 보고 비교하라. (B의 더미는 데이터 노드가 아니므로 병합 대상에서 제외한다.)
(2) 한쪽이 먼저 바닥났을 때 남은 쪽을 한 번에 붙이는 방법을 쓰라. 왜 하나씩 옮길 필요가 없는가?
(3) 위 예제의 비교 횟수를 세어라. 일반적으로 최대 몇 번인가?
(4) 복잡도를 쓰고, 배열 두 개를 합치는 것과 비교해 무엇이 유리한지 설명하라.
C2사이클 판정 — 토끼와 거북이
리스트의 어떤 노드가 앞쪽 노드를 다시 가리켜 고리가 생겼을 수 있다. 추가 배열을 쓰지 않고 O(N) 시간, O(1) 메모리로 고리의 유무를 판정하라.
(1) 한 칸씩 가는 포인터(거북이)와 두 칸씩 가는 포인터(토끼)를 동시에 출발시킨다. 고리가 있으면 왜 반드시 만나는가? (힌트 — 고리 안에서 둘의 간격이 매 걸음 어떻게 변하는가)
(2) 고리가 없으면 왜 반드시 끝나는가? 종료 조건을 정확히 쓰라.
(3) 1→2→3→4→5→6→7에서 7이 다시 3을 가리킬 때, 둘이 처음 만나는 노드의 값을 추적해 구하라.
(4) 만난 뒤 한 포인터를 맨 앞으로 되돌리고 둘 다 한 칸씩 가게 하면 고리의 시작점에서 만난다. (3)의 예로 확인하라.
(5) 전체 복잡도가 O(N)인 이유를 설명하라. 한 번의 반복에서 이동하는 링크 수가 상수이고, 고리 진입 전 경로와 고리 길이가 모두 N 이하임을 이용할 것. (단조 스택의 분할 상환 논증과는 다르다.)

두 문항이 겨냥하는 것

C1은 더미 헤드가 왜 유용한지를 몸으로 느끼게 하는 문제다. 더미 없이 짜 보면 “결과 리스트가 아직 비었는가”를 매번 검사하게 되는데, 기존 더미를 결과 헤드로 재사용하면 그 분기를 없앨 수 있다. 11장 병합 정렬에서 같은 병합 논리를 배열로 다시 만나므로 여기서 손에 익혀 둔다.
C2는 O(1) 메모리라는 제약이 핵심이다. 방문 표시 배열을 쓰면 쉽지만 메모리를 N만큼 쓴다. (5)는 빠른 포인터와 느린 포인터 사이의 상대 이동 거리로 만남을 설명하고, 각 단계의 이동 횟수가 O(N)임을 구분하여 증명해야 한다.

흔한 생각무엇이 틀렸나바로잡기
“리스트는 삽입이 O(1)이니 배열보다 빠르다”자리를 찾는 비용을 빼먹었다. 찾아서 넣으면 O(N)“위치를 이미 알 때”라는 조건을 함께 외운다 (4.1절)
“nxt[p]=q를 먼저 써도 되겠지”nxt[p]의 원래 값이 사라져 뒤가 끊긴다끊기 전에 먼저 붙잡는다. 삽입도 역순도 같은 규칙
“역순은 cur=nxt[cur]로 전진하면 된다”이미 뒤집어서 prev를 가리킨다 → 조용히 뒤가 날아간다after를 먼저 저장한다. 이 예시에서는 10 → NIL만 남는다

  • 논리적 순서와 물리적 순서가 왜 다른지 설명할 수 있다
  • 더미 헤드가 없애 주는 분기를 두 가지 말할 수 있다
  • 노드 풀 리스트 여섯 함수를 백지에서 작성할 수 있다
  • 역순 연결을 포인터 세 개로 짜고, ①을 빼면 왜 깨지는지 안다
  • 배열과 리스트의 복잡도 표 여섯 줄을 채울 수 있다
  • 노드당 메모리를 8바이트로 계산해 배열 크기를 정할 수 있다

다음은 10 이중 연결 리스트와 응용

이 장의 불편은 거의 전부 “뒤로만 갈 수 있다”에서 나왔다. 지울 노드가 아니라 앞 노드를 잡아야 했고, 그래서 find_prev 같은 함수가 필요했다.
10장에서는 prv 배열을 하나 더 두어 양방향으로 간다. 그러면 “이 노드를 지워라”를 O(1)에 할 수 있게 되고, 요세푸스와 에디터 시뮬레이션 같은 문제가 한 번에 풀린다. 4바이트 정수 배열 기준으로 노드당 원소 크기는 8 → 12바이트로 늘어난다. 포인터 기반 노드의 실제 크기는 환경과 정렬 조건에 따라 다르다. 그리고 10장이 PART 1의 마지막 장이다.
