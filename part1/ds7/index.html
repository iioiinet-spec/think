1왜 필요한가

스택이 “가장 최근”이었다면, 큐는 “가장 먼저”다. 한 글자 차이인데 구현이 꽤 달라진다.

1.1 줄 선 순서대로

큐(queue)는 줄이다. 뒤에 서고 앞에서 빠져나간다. 먼저 들어온 것이 먼저 나오므로 FIFO(First In, First Out)라고 한다.

상황줄 서는 것왜 순서대로인가
은행 창구번호표를 받은 손님먼저 온 사람이 먼저 받는 것이 공정하다
프린터인쇄 요청보낸 순서대로 출력된다
버퍼아직 처리 못 한 입력도착 순서를 지켜야 내용이 섞이지 않는다 (03장 입력 버퍼)
BFS (30장)발견되어 큐에 들어갔지만 아직 처리하지 않은 칸가까운 곳부터 퍼져 나가야 최단 거리가 나온다

마지막 줄이 이 장을 배우는 가장 큰 이유다. 모든 이동의 비용이 1로 같은 격자에서 BFS가 최단 거리를 보장하는 핵심 근거가 바로 큐의 FIFO 성질이고, 30장 전체가 이 위에서 돈다.

1.2 스택과 무엇이 다른가

스택 — 한쪽 끝만 쓴다

넣는 곳과 빼는 곳이 같다. 그래서 sp 하나만 움직이면 끝났다.

큐 — 양쪽 끝을 쓴다

넣는 곳(rear)과 빼는 곳(front)이 반대편이다. 그래서 표시가 두 개 필요하고, 여기서 문제가 생긴다.

표시가 두 개라는 사실이 이 장의 모든 내용을 만들어 낸다. 앞에서 빼면 앞쪽에 빈자리가 생기는데 그 자리를 다시 못 쓰는 문제(2.2절), 그것을 해결하는 원형 큐(2.3절), 그리고 원형이 되면서 생기는 “가득 참과 비어 있음이 똑같아 보이는” 문제(2.4절)가 차례로 나온다.

Q. 앞에서 뺄 때마다 전체를 한 칸씩 당기면 되지 않나요?
동작은 한다. 그런데 dequeue 한 번이 O(N)이 된다. 01장 연습 04에서 본 그대로다. N번 꺼내면 O(N²)이고, N = 10만이면 50억 번이라 시간 초과다. 큐의 모든 연산은 O(1)이어야 하고, 그래서 당기지 않고 표시만 옮기는 방법을 쓴다.

2개념과 그림

2.1 front와 rear

표시를 두 개 둔다. front는 다음에 꺼낼 자리, rear는 다음에 넣을 빈 자리다. 스택의 sp와 같은 약속(“다음 자리”)을 쓰므로 헷갈릴 일이 적다.

2.2 문제 — 뒤쪽이 차면 앞쪽의 빈칸을 못 쓴다

front와 rear가 둘 다 오른쪽으로만 가므로, 쓰다 보면 배열 왼쪽이 통째로 버려진다. 용량 5짜리 큐로 실제로 돌려 보자.

$ ./naive        용량 5짜리 선형 큐
enqueue 1 -> front=0 rear=1
enqueue 2 -> front=0 rear=2
enqueue 3 -> front=0 rear=3
dequeue 1 -> front=1 rear=3
dequeue 2 -> front=2 rear=3
dequeue 3 -> front=3 rear=3
지금 큐는 비어 있다 (front == rear == 3)
enqueue 4 -> 성공        (front=3 rear=4)
enqueue 5 -> 성공        (front=3 rear=5)
enqueue 6 -> 실패! 자리가 없다 (front=3 rear=5)

빈칸이 남았는데도 더 넣을 수 없다

dequeue 3 직후에는 큐가 비었다. push 4·5 뒤의 마지막 줄을 보자. 현재 큐에 든 것은 2개뿐이고 배열은 5칸인데 더 못 넣는다. rear가 배열 끝에 닿았기 때문이다. 앞쪽 0·1·2번 칸은 비어 있지만 이 선형 큐에서는 초기화하지 않는 한 다시 쓸 수 없다. 이것이 재사용이 필요한 상황에서 선형 큐가 불리한 이유다. 단, 전체 push 횟수 상한이 작다면 대회용 선형 큐도 유용하다.

2.3 해결 — 끝에서 처음으로 돌아간다

배열의 끝과 처음을 이어 붙여 원처럼 쓰면 된다. 구현은 한 글자, %다.

하던 것바꾼 것뜻
rear = rear + 1rear = (rear + 1) % CAP끝(CAP−1) 다음이 다시 0이 된다
front = front + 1front = (front + 1) % CAP

CAP = 5일 때 인덱스는 0→1→2→3→4→0→1→… 로 돈다. 나머지 연산 하나로 배열이 원이 된다. 그런데 원이 되는 순간, 새로운 문제가 생긴다.

2.4 새 문제 — 가득 참과 비어 있음이 똑같아 보인다

선형 큐에서는 front == rear가 “비었다”였다. 그런데 원형으로 만들면 배열 CAP칸을 전부 채우면 front == rear가 되어 비어 있는 상태와 구별되지 않는다.

해결책은 두 가지다. 둘 다 널리 쓰이고 각각 장단점이 있다.

방식 A — 한 칸을 비워 둔다

절대 가득 채우지 않는다. 배열이 CAP칸이면 최대 CAP−1개만 담는다. 그러면 front == rear는 오직 “비었다”일 때만 생긴다.

판정조건설명
비었다front == rear그대로
가득 찼다(rear + 1) % CAP == front한 칸 남았을 때를 “가득”으로 본다

방식 B — 개수를 따로 센다

변수 cnt를 하나 더 두고 넣을 때 +1, 뺄 때 −1 한다. 배열을 전부 쓸 수 있다.

판정조건설명
비었다cnt == 0front와 rear를 비교할 필요가 없다
가득 찼다cnt == CAP

방식 B는 rear를 아예 두지 않아도 된다. 넣을 자리는 (front + cnt) % CAP로 계산할 수 있다(CAP > 0). push 전에는 cnt < CAP, pop·front 전에는 cnt > 0이어야 한다.

실제로 돌려 보면

$ ./circ          배열 칸 수 = 5
[방식 A] 한 칸 비우기            [방식 B] 개수 세기
push 1~4 -> 성공                 push 1~5 -> 성공
push 5   -> 가득 참              push 6   -> 가득 참
최대 저장 개수 : 4개             최대 저장 개수 : 5개

어느 쪽을 쓸까

방식 B를 권한다. 배열을 다 쓸 수 있고, cnt 덕분에 현재 개수를 언제든 O(1)에 알 수 있다(이것이 의외로 자주 필요하다). 방식 A는 변수가 하나 적지만, “왜 한 칸이 모자라지?”로 헷갈리는 사고가 잦다. 다만 방식 A도 널리 쓰이므로 남의 코드를 읽을 때를 대비해 둘 다 알아 둔다.

3구현

3.1 원형 큐 — 방식 B (권장)

/* circq_b.c — 방식 B: 개수로 빈 큐/가득 찬 큐 구별 */
#include <assert.h>
#define CAP 100005
static int q[CAP];
static int qf, qcnt;   /* front 위치, 저장된 원소 수 */

static int q_empty(void){ return qcnt == 0; }
static int q_full(void) { return qcnt == CAP; }
static int q_size(void) { return qcnt; }
static void q_push(int x){
    assert(!q_full());  /* 가득 차면 넣지 않는다 */
    q[(qf + qcnt) % CAP] = x;
    ++qcnt;
}
static int q_pop(void){
    assert(!q_empty()); /* 비면 꺼내지 않는다 */
    int x = q[qf];
    qf = (qf + 1) % CAP;
    --qcnt;
    return x;
}
static int q_front(void){
    assert(!q_empty());
    return q[qf];
}
static void q_clear(void){ qf = qcnt = 0; }

(qf + qcnt) % CAP가 넣을 자리인 이유

맨 앞이 qf이고 qcnt개가 들어 있으니, 마지막 값은 qf + qcnt − 1번 자리에 있다. 그 다음 칸이 qf + qcnt이고, 배열을 넘어가면 %로 되돌린다. rear 변수를 따로 두지 않아도 되는 이유가 이것이다.

3.2 원형 큐 — 방식 A (한 칸 비우기)

아래 구현은 방식 B와 이름이 같은 별개의 대안이다. 두 코드를 한 C 파일에 동시에 넣지 말고 각각 독립 실행 파일에 사용한다. 두 방식 모두 assert를 이용해 사전조건을 확인한다.

/* circq_a.c — 방식 A: B와 별도 파일로 사용 */
#include <assert.h>
#define CAP 100005  /* 실제로 담을 수 있는 수: CAP-1 */
static int q[CAP], qf, qr;

static int q_empty(void){ return qf == qr; }
static int q_full(void){ return (qr + 1) % CAP == qf; }
static void q_push(int x){
    assert(!q_full());
    q[qr] = x;
    qr = (qr + 1) % CAP;
}
static int q_pop(void){
    assert(!q_empty());
    int x = q[qf];
    qf = (qf + 1) % CAP;
    return x;
}
static int q_size(void){ return (qr - qf + CAP) % CAP; }
static void q_clear(void){ qf = qr = 0; }

q_size에 + CAP가 붙은 이유

qr이 한 바퀴 돌아 qf보다 작아질 수 있다. 그러면 qr − qf가 음수가 되는데, C에서 음수에 %를 쓰면 음수 나머지가 나온다(예: -2 % 5는 −2). 그래서 CAP을 더해 양수로 만든 뒤 나눈다. 원형 큐에서 음수 모듈러는 가장 흔한 버그이고, 08장 덱에서 front를 왼쪽으로 옮길 때 다시 만난다.

용량이 N개 필요하면 배열은 N+1칸으로 잡아야 한다. assert 검사는 -DNDEBUG 옵션에서 비활성화되므로, 실제 입력이 잘못될 수 있는 프로그램에는 명시적인 오류 반환·검사도 필요하다.

3.3 대회 실전형 — 밀지 않는 선형 큐

의외의 사실 하나. 대회에서는 원형 큐를 안 쓰는 경우가 더 많다. 배열을 충분히 크게 잡고 % 없이 그냥 쓴다.

/* linearq.c — 밀지 않는 선형 큐 */
#include <assert.h>
#define MAXQ 1000005
static int q[MAXQ];
static int qf, qr;

static void q_push(int x){
    assert(qr < MAXQ);  /* 총 push 횟수 제한 */
    q[qr++] = x;
}
static int q_pop(void){
    assert(qf < qr);    /* 비어 있지 않을 것 */
    return q[qf++];
}
static int q_empty(void){ return qf == qr; }
static int q_size(void){ return qr - qf; }
static void q_clear(void){ qf = qr = 0; }

세 구현의 q_push·q_pop은 각각 별도의 코드 예시이다. 용량 초과·빈 큐 접근은 사전조건 위반이며, 예제에서는 assert로 검사한다. 실제 입력이 잘못될 수 있는 경우에는 오류 반환값을 직접 처리해야 한다.

이게 왜 괜찮은가 — 들어가는 총 개수를 세어 본다

배열이 낭비되는 것은 맞지만, 중요한 것은 “전체에서 push가 몇 번 일어나는가”다. 방문 표시를 큐에 넣을 때 하는 표준 BFS(30장)는 각 정점이 많아야 한 번 들어가므로 배열 크기는 정점 수면 충분하다.

반대로 같은 값이 여러 번 드나드는 문제에서는 총 push 횟수를 따로 세어야 한다. 요세푸스가 그렇다.

$ ./grow        요세푸스 (k = 3), 밀지 않는 선형 큐가 쓴 배열 칸 수
n=   1,000  ->    3,000칸  (n의 3.0배)
n= 100,000  ->  300,000칸  (n의 3.0배)
n=1,000,000 -> 3,000,000칸 (n의 3.0배)

총 push 횟수 = n × k (아래 코드 그대로 실행할 때)

처음 n명을 넣는 push가 n번, 한 명을 제거하기 전에 k−1번씩 뒤로 보내는 push가 총 n(k−1)번이다. 따라서 총 push = n+n(k−1)=nk번이며, 선형 배열은 적어도 nk칸이 필요하다. 이 코드는 마지막 한 명도 k−1번 회전시킨다. k = 3이면 3n이라 괜찮지만 k가 100이면 100n칸이라 위험하다. “선형으로 충분한지”는 총 push 횟수로 판단한다. 큐를 중간에 안전하게 초기화하면 새 사용 구간마다 다시 계산한다.

3.4 응용 — 요세푸스 문제

1번부터 n번까지 둥글게 앉아 있고, k번째 사람을 차례로 제거한다. 제거되는 순서를 출력한다. 조건: n ≥ 1, k ≥ 1. 아래 코드는 가득 차지 않는 충분한 용량의 원형 큐(B) 또는 총 push 횟수 nk를 담을 수 있는 선형 큐를 전제로 한다.

for (int i = 1; i <= n; i++) q_push(i);
while (!q_empty()) {
    for (int i = 0; i < k-1; i++) q_push(q_pop());  /* k-1명을 뒤로 */
    printf("%d ", q_pop());                        /* k번째를 제거 */
}
$ ./jose
<7, 3> 요세푸스 : <3, 6, 2, 7, 5, 1, 4>

코드 한 줄이 문제를 그대로 옮긴다

q_push(q_pop())는 “맨 앞 사람을 꺼내 맨 뒤에 세운다”, 즉 원을 한 칸 돌리는 동작이다. 01장의 “동사를 먼저 뽑는다”가 그대로 코드가 된 예다.

4복잡도 분석

4.1 연산별 비용

연산복잡도설명
push · popO(1)표시 하나를 옮기고 나머지 연산 한 번
front · empty · sizeO(1)변수를 읽거나 뺄셈 한 번
가운데 보기제공 안 함ADT가 금지한다
(참고) 당기는 방식O(N)dequeue마다 전체를 밀면 N번에 O(N²)

4.2 메모리 — 어느 구현을 고를지의 기준

구현필요한 배열 칸변수고르는 기준
선형 (밀지 않음)총 push 횟수2개총 push가 적으면 1순위. BFS는 정점 수로 충분
원형 A (한 칸 비움)최대 동시 개수 + 12개메모리가 빠듯하고 변수를 줄이고 싶을 때
원형 B (개수 셈)최대 동시 개수2개메모리가 빠듯할 때. 개수를 자주 쓰면 유리

판단 순서

  1. 총 push 횟수를 센다. 각 원소가 한 번만 들어간다면(BFS 등) → 선형으로 충분
  2. 여러 번 들어갔다 나온다면 총 push 횟수를 계산한다 (요세푸스는 n × k)
  3. 그 값이 메모리 제한을 넘으면 → 원형 큐로 바꾸고 배열은 최대 동시 개수만큼만 잡는다

4.3 요세푸스의 복잡도

위 구현은 n명을 처음 넣고, 매 제거마다 k−1번 회전한 뒤 한 번 더 꺼낸다. 따라서 push가 nk번, pop도 nk번으로, 총 큐 연산은 약 2nk번이고 시간복잡도는 O(nk)다. n=100만, k=100이면 약 2억 번의 큐 연산에 출력까지 필요하므로 1초 통과를 장담할 수 없다.

예제 2 음수 모듈러

방식 A에서 q_size를 (qr - qf) % CAP로 썼다. CAP = 5, qf = 3, qr = 1일 때 (1) 실제 개수는? (2) 이 식의 결과는? (3) 올바른 식은?

풀이. 배열 상태를 그려 보면 자리 3, 4, 0에 값이 있고 1이 다음 빈 자리다.

  • (1) 실제 개수는 3개 (자리 3, 4, 0)
  • (2) (1 - 3) % 5 = (-2) % 5 = −2. C는 음수 나머지를 그대로 돌려준다
  • (3) (qr - qf + CAP) % CAP = (1 - 3 + 5) % 5 = 3 % 5 = 3

일반 규칙. C에서 %의 결과는 왼쪽 피연산자의 부호를 따른다. 그래서 음수가 될 수 있는 값에 %를 쓸 때는 먼저 CAP을 더해 양수로 만든다. 08장 덱에서 front를 왼쪽으로 옮길 때 (qf - 1 + CAP) % CAP로 똑같이 처리한다.

흔한 생각무엇이 틀렸나바로잡기

“(qr - qf) % CAP로 개수를”음수가 나올 수 있다. C의 %는 왼쪽 부호를 따른다(qr - qf + CAP) % CAP
“방식 A에서 1,000개면 배열 1,000칸”한 칸을 비워 두므로 999개가 한계다필요한 개수 + 1칸을 잡는다
“선형 큐 배열은 동시 최대 개수만큼”선형 큐는 총 push 횟수만큼 필요하다총 push를 세고, 크면 원형으로 바꾼다

“clear는 없어도 돼”여러 테스트를 연달아 돌리면 qf·qcnt가 이전 상태를 유지해 오답이 난다. 배열에 남은 옛 값 자체는 비어 있는 칸이라 무관하다qf = qcnt = 0 한 줄을 반드시 둔다

자가 점검

  • 선형 큐에서 자리가 소진되는 과정을 그림으로 설명할 수 있다
